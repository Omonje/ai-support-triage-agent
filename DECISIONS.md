# Decisions

Record a decision only when it is hard to reverse, a later reader would ask "why?", and there was a real trade-off.

## Decision log
| # | Decision | Chosen | Instead of | Why | What we give up |
|---|---|---|---|---|---|
| 1 | Inbox integration | Real Gmail API, scoped to a dedicated label | A local SQLite mock inbox | A real API integration is a stronger, more demoable production-readiness signal than a mock, matches the "production-ready, realistic" bar for this round of portfolio builds | Added setup cost (Google Cloud OAuth client), and the demo depends on a real external API instead of a fully controlled local stand-in |
| 2 | Niche framing | Manufacturers | Generic / another already-covered niche | Zero existing portfolio coverage for this niche; gives classification categories real texture (order status, defect complaint, quote request, urgent delay) | None significant |
| 3 | LLM provider | Claude API | OpenAI or another provider | Consistent with an earlier build, reuses existing API familiarity | None significant |
| 4 | Audit log + approval queue tool | monday.com, new account (Free plan) | Airtable (rejected, overused across her other portfolio pieces), Notion (database model doesn't naturally fit a live status-driven queue) | Needed a client-visible tool, not a local file. monday.com's task/status model maps directly onto "classified -> draft ready for approval -> sent/escalated," which Airtable and Notion would have to bend to fit | None at this scale; would need a paid plan only if this became a real high-volume deployment |
| 4b | Correction (2026-10-xx) | — | — | The "confirmed Free plan" check on 2026-10-02 read an account that was actually mid-trial of a paid plan, not genuinely Free; the trial has since expired and hit a paywall. New account being created to get a real Free plan. Logged so this isn't mistaken for a stable fact later | — |
| 4c | monday.com has no real Free tier reachable through signup | Build on the Pro CRM trial, time-boxed, record a video and screenshots before it expires | Switching to ClickUp (genuine permanent free tier) | The new account (demo-account@example.com) auto-enrolled into the same Pro/CRM trial pattern as the first account, there is no plain Free path through monday's signup. Finishing on the trial is faster than a third account-creation cycle | The live board will stop being viewable/demoable once the trial ends and locks; the case study has to rely on the recorded video and screenshots captured during the trial window, not a live link |
| 5 | KB retrieval method | TF-IDF + cosine similarity (scikit-learn) | Learned embeddings (sentence-transformers / an embeddings API) | A 15-article fixed policy KB is exactly the case where keyword/term overlap is already a strong, explainable signal; embeddings would add a heavy dependency (torch) and, in practice, an unreliable download in this environment for no real gain at this scale | Won't catch pure paraphrase with zero shared vocabulary; acceptable for a demo-scale KB, would revisit if the KB grew large or became more free-form |
| 6 | LLM provider, made swappable | Gemini (Flash, free tier) as the active provider for the live demo; Claude kept as a fully working alternative behind the same gateway interface | Staying Claude-only and waiting until there's money for credits | No Anthropic credits available (2026-10-06: "Your credit balance is too low to access the Anthropic API"). Gemini's free tier (aistudio.google.com) needs no card, 1,500 req/day on Flash, far more than this demo uses. Both ClaudeGateway and GeminiGateway implement the identical two-method interface (classify_message, draft_reply) against shared prompts in `app/gateways/llm_types.py`, so the pipeline and service layer never know which one answered; `LLM_PROVIDER=claude\|gemini` in `.env` is the only switch | Gemini's free tier allows the request data to be used for Google's model training; fine here since every message is synthetic, but a real client deployment handling real customer data would need the paid tier instead. Documented in the case study's honest-limits section, not glossed over |
| 7 | LLM provider, switched again | Groq (free tier, Llama 3.3 70B) as the active provider | Staying on Gemini, spacing the 18-message run across several days | 2026-10-08's real run proved the account's actual available Gemini model (gemini-3.8-flash) is capped at 20 requests/day, which a single run burns through by itself (most messages need 2 calls, plus retries on transient 503s), so waiting for the daily reset doesn't fix it. Groq's free tier has a far higher daily cap and needs no card. Added `GroqGateway` behind the exact same two-method interface, a third interchangeable adapter, no change to any business logic. `LLM_PROVIDER=claude\|gemini\|groq` in `.env` is still the only switch | Another provider to document as a stand-in choice in the case study; Gemini and Claude both remain fully wired and tested if either is needed again |
| 8 | Human notification | A Slack incoming webhook, optional (`SLACK_WEBHOOK_URL`), wired as a fourth small gateway | monday.com's own built-in notifications (zero code, but invisible to anyone reviewing the build); no alert at all (documented as a limit) | The system had no push signal at all, a human had to proactively check the monday.com board or Gmail Drafts folder, which is a real gap for the one thing that most needs fast attention: an escalated defect complaint. One alert per escalation (immediate, since each is individually safety-relevant), one summary alert per run for routine drafts (not one per message, to avoid spamming a channel on an 18-message batch). The alert is best-effort: if Slack itself is down, the escalation label, the monday.com item, and marking the message processed all still happen, only the notification is skipped and logged | Another optional external dependency and webhook to manage; if `SLACK_WEBHOOK_URL` is unset the pipeline runs exactly as before with no alerts, so this never becomes a hard requirement |
| 9 | Pipeline-failure visibility | A third Slack alert type (summary of failed messages, same run-end alert as the draft summary) plus wiring the existing structured JSON logger into a durable `pipeline.log` file via `run_pipeline.py` | Leaving failures console-only (the prior state) | The question "how does the team know there's a problem with the workflow" exposed that a whole-run failure (e.g. the LLM provider down, which has happened twice in testing) produced only console `[FAILED]` lines nobody but the person actively watching the terminal would see, and the structured logger already built in `app/logging_setup.py` was wired only into the unused FastAPI health-check stub (`app/main.py`), never into the script that actually runs. Both gaps closed without inventing new infrastructure, reusing the Slack gateway and the logger that already existed | `pipeline.log` grows unbounded with no rotation, acceptable at this demo's run frequency and scale; a real deployment would want log rotation and a log aggregator instead of a flat file |
| 10 | Deployment, off the local machine | GitHub Actions, a private repo (`github.com/Omonje/ai-support-triage-agent`) with a scheduled workflow (every 30 min, plus manual trigger) running the real pipeline against the live accounts, secrets stored in GitHub's encrypted repo secrets; a second workflow runs the full test suite on every push | A deployed FastAPI host (Render/Railway) with an external scheduler hitting a trigger endpoint | The user wanted this to actually run somewhere live, not only when she happens to run a script on her laptop, so it genuinely looks like something built for a client rather than a local demo. GitHub Actions needed no new hosting account, handles secrets properly, and closed TESTS.md's long-standing "CI not set up yet" gap for free in the same move. Verified for real: a manual trigger authenticated to Gmail, Groq, and monday.com entirely from GitHub's own runners | `gmail.modify` is a Restricted OAuth scope (confirmed against Google's own docs), so while the app stays in Testing publishing status, the only realistic option short of an annual third-party security audit, its cached refresh token expires roughly every 7 days. The scheduled workflow will need a quick manual re-consent on that cadence (re-run the interactive flow locally once, update the `GMAIL_TOKEN_JSON` repo secret); if it lapses, the newly added startup-failure Slack alert (see #9) surfaces it immediately instead of the workflow silently going quiet |
| 11 | Knowledge base storage | Supabase (free-tier Postgres), read through its auto-generated REST API with the `service_role` key | Google Sheets (simpler, but feels less like coded engineering); staying on the local JSON file | Same motivation as #10: a knowledge base that only exists as a file on one laptop undercuts the "built like it's for a client" story just as much as a manually-run script did. `SupabaseKBRepo` follows the exact same thin-REST-gateway pattern as every other gateway in this project (Gmail, monday.com, Slack), no new SDK dependency, just `requests`. A one-time migration script upserts the 15 local articles into a new table (created by hand in Supabase's SQL editor, since PostgREST has no DDL support, only CRUD on existing tables). `SUPABASE_URL`/`SUPABASE_SERVICE_KEY` are now required config, not optional, since the whole point is no longer falling back to a local file | One more free-tier account and secret pair to manage; `data/kb_articles.json` stays in the repo as the migration's source data and a record of the original seed content, not as the runtime source anymore |

## Decisions I should be able to defend
For each: the question someone will ask, and my answer in my own words.

| Question | My answer |
|---|---|
| Why a real Gmail integration instead of mocking it like the other builds? | Gmail's API is free, well-documented, and scoping to a single label keeps it safe. A real integration is more credible proof than a mock, and "draft for approval" maps directly onto a real Gmail draft rather than an invented internal UI. |
| Whose Gmail account is this running against? | A dedicated account/label set up only for this demo, never my real inbox or any real client's, and every message in it is synthetic, written for this project. |
